## 初回導入

プロジェクト直下で実行する。既存の`.local-validation/`・`validation/.venv/`、秘密情報、DB保存領域は利用しない。新規領域は`backend/.venv/`、`frontend/node_modules/`、`.m0-cache/`。これらはGit対象外。

必要なランタイムはPython 3.13.13、Node.js 24.21.0、npm 11.19.0。Nodeは`.node-version`、Pythonは`backend/.python-version`に記録。Mac arm64で導入・検査済み。Azureの提供版・Linuxでの再導入はM2／M6で別途確認する。

```sh
python3.13 -m venv backend/.venv
fnm --fnm-dir .m0-cache/fnm install 24.21.0
make install
make check
make build
make smoke
```

Pythonが既に3.13.13かは`python3.13 --version`で確認する。Nodeを既に指定版で導入している場合はfnmの行を省略できる。`tools/frontend.sh`は新規の専用Node領域を優先し、なければPATH上のNodeを版確認して使う。システムのNode既定版は変更しない。

`make install`はPythonの全開発依存をハッシュ検証付きで導入し、npmは`npm ci --ignore-scripts`でロックどおり再導入する。npmの任意ライフサイクルスクリプトは実行しない構成でbuildと起動を確認する。生成物・既存node_modulesはソースの正本ではない。

## 起動・検査

| コマンド | 内容 |
|---|---|
| `make dev-backend` | FastAPIを127.0.0.1:8000で起動。終了はCtrl-C |
| `make dev-frontend` | Next.js開発サーバーを127.0.0.1:3000で起動。終了はCtrl-C |
| `make lint` | Ruffの静的検査・整形確認、ESLintのJS／TypeScript／Next規則 |
| `make typecheck` | バックエンドappのmypy strict、Next型生成＋TypeScript strict |
| `make test` | バックエンド単体・ASGI試験とフロント中継試験（実DB・実機試験は別途） |
| `make contract` | 正本OpenAPIを専用検証器で検査。外部$refは拒否し、ソースを送信しない |
| `make check` | lint・型・単体・OpenAPIを順に検査。失敗時点で停止 |
| `make build` | Python sdist／wheelとNext.jsの最適化buildを生成 |
| `make start-frontend` | build済みNext.jsを127.0.0.1:3000で起動 |
| `make smoke` | 空きローカルポートで両サーバーを起動、HTTP応答・終了後の接続不能を確認。終了後にサーバーを残さない |

起動確認ではフロントに準備中ページ、バックエンドに業務ルートのないFastAPIを置く。商品／会員・購入APIは公開しない。404はM0の未実装確認であり、M2の認証拒否401を実証した意味ではない。現在のHTTP起動は開発用で、Secure Cookie・カメラのHTTPS確認に代用しない。

## 固定版と更新

- Python：`backend/requirements.in`が本番直接依存、`requirements-dev.in`が開発ツール。`requirements.lock`と`requirements-dev.lock`が間接依存を含む版・配布物ハッシュの正本。現在の解決対象はPython 3.13／macOS arm64。Linux x86_64ではSQLAlchemyのgreenlet等の環境条件が変わるため、配備前に対象環境で固定・監査・起動を再確認する。
- npm：`frontend/package.json`は直接依存を完全版で指定。`package-lock.json`はプラットフォーム別optional依存も含め固定。`--force`や`--legacy-peer-deps`で互換性エラーを無視しない。
- 更新時は公開ライセンス・保守状況・脆弱性と相互依存を確認し、影響する検査を再実行。今回の結果は[evidence/m0](evidence/m0)に保存する。

Pythonロック更新（M0で導入したpip-toolsを使用）：

```sh
backend/.venv/bin/pip-compile --allow-unsafe --generate-hashes --strip-extras --no-emit-index-url --output-file backend/requirements.lock backend/requirements.in
backend/.venv/bin/pip-compile --allow-unsafe --generate-hashes --strip-extras --no-emit-index-url --output-file backend/requirements-dev.lock backend/requirements-dev.in
```

依存ロックは本番の動作や安全性の保証ではない。今回の公開脆弱性照会はパッケージ名・版だけをOSVへ送り、プロジェクトのソース・文書・認証情報は送っていない。カメラ依存はまだ利用しないため未導入で、M5前の採用時に再確認する。

## 設定例

`backend/.env.example`・`frontend/.env.example`はM2で使う設定項目の一覧で、接続可能な秘密値は入っていない。M0の起動処理はこれらを読み込まない。中継秘密値はサーバーだけに渡し、`NEXT_PUBLIC_`へ設定しない。DB接続・TLS検査・Origin完全一致・中継保護はM2で設計契約に沿って実装する。

## M2の検証環境案と開始条件

推奨案は、まず新規のローカルMySQL 8.4インスタンスでDB制約・認証・初回開始を確認し、Azure上のTLS・権限・性能はM2後半〜M6で確認する。以下は対象を具体化した準備案で、まだDBや証明書は作成していない。

| 項目 | 準備案・条件 |
|---|---|
| DB対象 | Docker CLIの存在だけを確認済み。新規コンテナ名`tech0-pos-m2-mysql`、新規専用volume名`tech0-pos-m2-mysql-data`、DB名`pos_validation`。既存名との衝突時は停止。既存コンテナ・volumeを流用しない |
| 版・費用 | MySQL 8.4の提供イメージとdigestをM2開始時に確認。ローカル資源を使いAzureリソースを作らない案。Dockerの稼働可否・利用条件・空き容量は未確認。Azure案を選ぶ場合は実契約費用と対象を確認 |
| 接続 | DBはホスト127.0.0.1:3307からのみ接続する案。ブラウザへDBを公開しない。TLS証明書とホスト名を検証、UTC・READ COMMITTED・厳格SQL。TLSを無効にして受入条件を迂回しない |
| データ | 既存の16表DDLを新規DBに適用。架空担当者／会員／商品だけを使用。初回・通常・特定状態をテスト実施条件に従って別管理。売上や復帰記録を自動初期化しない |
| 権限 | DDL適用・マスタ管理・通常アプリで別アカウント。通常アプリ権限は設定別紙3節の表単位の範囲。秘密値はGit除外領域へ保持、シェル履歴・ログに残さない |
| HTTPS | Mac／iPhone両方から同じ専用検証ホストへアクセスできる証明書・経路を選定。localhost HTTPは代用不可。LAN公開、端末への証明書信頼設定、実機操作は対象を明示して実行前に確認 |
| Q04実証 | 初回Cookie確認→同一context/cart復帰と、別紙5.1の手動Cookie修復を分ける。iPhone 15とMacのChrome版・OS版を実行時に記録。本人の実機利用枠は未指定 |
| 完了確認 | DDL・16表・制約・初期件数・権限・TLS・接続先を確認してから、ログイン→初回Cookie→空カートへ進む |
| 中止・戻し | 作成／起動した新規プロセスだけを停止。DDLや投入失敗は対象DBを確認し証跡を保持。既存DB・volumeは触らず、新規volumeも自動削除しない。削除・復元は別の対象確認後 |

次回M2ではこの案を実行可能な構成・投入手順へ仕上げてから、DB作成とHTTPS・実機操作の対象を確認する。M0の完了と、M2環境の実行許可・実証済み状態は区別する。

M2では設定例の変数を実装が読む。バックエンドは環境変数を読むだけで.envファイルを自動ロードしない。フロントはNext.js標準の環境設定を使用する。設定なしではAPIは503となり、Cookie保護を外した開発モードは設けない。`make smoke`はこの停止動作とプロセス起動を確認する。
