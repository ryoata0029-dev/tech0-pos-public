## 自動解放の成立条件

主担当は既存のmember-late wrapperを設置後、`oct05_member_fixture.install()`を1回呼ぶ。既存wrapperの実受付後保留、実lookup完了後・反映前保留を維持する。その外側で観測するため、新選択の実トランザクション終了後にだけ私有releaseを作る。

```sh
backend/.venv/bin/python tools/oct05_mac.py arm --kind member-late --tag o05-m-l1
M2_LOCAL_PROFILE=oct05-mac backend/.venv/bin/python tools/oct05_member_fixture.py arm --tag o05-m-l1 --cart-id <今回のcart UUID> --new-member member0
```

上の既存gate用wrapper名は主担当が登録した`oct05_mac.py`である。実行時に固定profile・dispatchを確認する。L2は新tag`o05-m-l2`と`--new-member nonmember`を使う。今回cart UUIDを正規応答／独立DBから得て、過去IDを流用しない。

自動解放は次の全条件を必要とする。

- 同一cartの旧MEMBER_1受付が実PREPARED／PENDINGで確定し、旧operation ID・版・保持行を保存済み。
- 同tag／旧operationの実lookupがfound=trueで終了し、更新トランザクション外で反映前保留中。旧hold時刻が新選択COMMIT後の観測時刻より早い。
- 通常PUT memberの新operationが旧operationと異なる。新MEMBER_0はCONFIRMED／APPLIED・旧受付版＋2、非会員はNON_MEMBER／APPLIED・旧受付版＋1。pending IDはnull。line ID／行番号／code／数量／単価／税率は受付時と一致。
- 未使用control、未作成release・commit証跡のみ。readonly、別メソッド／path／cart、PREPARED、別会員、REJECTEDでは解放しない。

成立時に`member-new-commit-<tag>.json`→私有`release-<tag>.json`→`member-auto-release-<tag>.json`を作り、元の実APPLIED応答をそのまま返す。証跡や版の不整合はfixture失敗として停止する。新選択のCOMMITを取り消さず、疑似の正常結果や自動再送を作らない。markerの生成だけではChromeへの旧応答到着を証明しない。

## 必要証跡と判定限界

通常POS A/Bの送信・PENDING・新選択・通知停止・正規再確認後のDOM／画像、CUAの通常操作trace、開始／終点のDBを採取する。既存`gate`・`lookup-held`・`lookup-released`・`lookup-finished`に、今回の`member-old-receipt`・`member-new-commit`・`member-auto-release`を合わせ、cart／旧新operation／版／数量・価格・税・期待金額を照合する。全tag・ID・source/build hash・UTCは試行ごとに固定する。

Chrome DevToolsの正規Network UIで旧member PUTのstatus409とResponse JSONの`MEMBER_LOOKUP_SUPERSEDED`を保存する。Headers／Cookie／Request payloadは保存しない。同名PUTの旧新を開始順・status・時刻で区別できない場合は生HTTP到着を未確認とする。旧要求開始→lookup hold→新COMMIT→release→旧finish／返却の順と、旧要求開始から返却まで10秒未満を照合する。これにChromeの行／本文が揃って初めて直接受信を確認とする。

自動release直前に新選択後の独立DB9集合snapshotを挟むことは前提にしない。新COMMITの実APPLIED metadata、旧finishの実REJECTEDと同版／同会員／金額、終点DBで不反映を照合する。新選択後・旧finish前後の独立snapshot2点が実際に揃った場合だけ、9集合の完全不変を主張する。前日の長時間保留snapshotを今回へ流用しない。限られた保持行projectionは全値引き候補・条件時刻の一致を単独では証明しないので、開始／終点DBで別に照合する。
