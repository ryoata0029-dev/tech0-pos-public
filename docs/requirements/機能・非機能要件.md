## 3. 機能・データ要件

出典IDを要件識別にも用いる。

<a id="sec-3-1"></a>

### 3.1 操作・表示

<a id="r-topic-01"></a>

#### ログインと担当者・会員の表示

関連：F01・F02・F03

- 専用画面で担当者ID・パスワードによるログインを行う。
- 認証情報はシステム単独で管理し、外部ID基盤は使わない。
- 通常のログインでは、正しい情報なら購入リストが空・会員未指定のPOS画面へ進み、すぐに商品登録できる（U02）。
- 誤りならログインさせず、[4.2](#sec-4-2)の共通エラーを表示する。
- POS画面にはログイン中の担当者情報と顧客の会員IDを表示する。

<a id="r-topic-02"></a>

#### 会員情報と指定方法

関連：F04・F05・F06・F07

- 会員ID・氏名・電話番号・住所・性別・年齢は全て必須の登録済み属性とし、NULL・空文字を認めない。
- 年齢は0以上の整数。
- 性別の選択肢や独自の文字数・年齢上限は追加せず、保存先の型の範囲内とする。
- 会員IDは手入力・バーコードで購入確定前の任意の時点に指定でき、未指定でも非会員購入ができる。
- 照会・変更時は下表に従う。

<a id="r-topic-03"></a>

#### 会員照会・変更（F04〜F07・U01）

- 照会開始から会員未確定として商品追加・数量変更・削除・購入確定を止め、購入リストを保持する。
- 入力候補と従来の会員を区別し、旧会員を現在適用中として表示しない。
- 旧値引き・合計を残す場合は「変更前の参考額・会員確認待ち」と明示する。
- 最初の会員指定にも同じ制限を適用する。

| 照会結果・選択 | 表示・復帰動作 |
|---|---|
| 確認成功 | 新しい会員へ切り替え、商品行の保持条件で再計算する。購入可能となる |
| 会員不存在 | 「会員が見つかりません」と表示し、再入力または非会員を選べる |
| 通信障害等で確認不能 | 不存在と区別して確認不能を表示し、再照会または非会員を選べる |
| 非会員を明示選択 | 旧会員を含む会員ID・特典を解除し、購入可能となる |

- 不存在・確認不能では旧会員へ自動的に戻さない。
- 会員確認待ちの間も再入力・再照会・明示的な非会員選択は可能。
- 確認成功または非会員選択で会員確認による制限を解除するが、他の操作制限は維持する。
- 別タブ・APIにも同じ制限を適用する。
- 別の会員指定・非会員選択へ進んだ後の古い照会結果は反映しない。

<a id="r-topic-04"></a>

#### 商品検索・読取

関連：F08・F09

- 商品コードを手入力して検索し、一致する商品の名称・単価を表示する。
- 未登録ならその旨を表示する。
- カメラでバーコードを読み取れ、認識成功時には1件追加されたことが分かる反応を示し、続けて次の商品を読み取れる。

<a id="r-topic-05"></a>

#### 購入リストへの追加

関連：F10・F11・F12

- 商品追加時、購入リストにない商品は新しい行に追加し、同じ商品は既存行の数量を増やす。
- 手入力とスキャンで同じ扱いとする。
- リストには名称・数量・単価・小計を表示する。
- 追加後は商品コード入力・名称表示・単価表示をクリアする。

<a id="r-topic-06"></a>

#### 商品連続読取（F09・F10）

- 1件の追加成功後、押下なしで次の異なる商品を読み取れる。
- 同じコードが映り続ける間は重複加算せず「同じ商品です」と表示する。
- 同じ商品をもう1個追加するには一度枠から外して再提示し、同一行の数量を1増やす。
- 数量変更でも対応できる。
- 通信結果不明中や他の操作制限中は次を受け付けない。

<a id="r-topic-27"></a>

#### 数量変更・削除

関連：F13・F14・F15

- 購入リストの1商品を選択でき、選択行を見分けられ、名称・単価・数量を確認できる。
- 選択商品は削除または数量1〜99への変更ができる。
- 数量0にはせず、除去には削除を使う。
- 数量変更を小計・全体の合計金額に反映する。
- 手入力・スキャンによる追加にも上限99個を適用し、超過する追加は行わず、その旨をエラー表示して数量を保持する。

<a id="r-topic-08"></a>

#### 購入結果の表示・次取引

関連：F23・F24

- 購入確定時に税抜・税込合計を提示し、税込合計はポップアップ等で表示する。
- これを閉じると商品コード入力・名称表示・単価表示・購入リスト・会員ID・会員特典の適用状態をクリアし、担当者のログインを維持して次の取引へ進める（U02）。

<a id="sec-3-2"></a>

### 3.2 金額計算

| 出典ID | 要件 |
|---|---|
| F16・F17・F18 | 会員に対し、対象商品・適用期間に応じた割合割引または定額値引きを適用する。購入までに会員IDを指定すれば特典を適用し、購入リストに値引き額を表示する。対象商品・期間・内容はコード変更なしで変更・追加できる。 |
| F25・T01 | 消費税率をデータとして保持し、コード変更なしで変更できる。商品ごとに適用税率を設定し、異なる税率の商品を同じ取引で購入できる（T01）。 |

<a id="r-topic-09"></a>

#### 単価・税率・値引き条件の適用時点（T01）

商品単価は税抜として扱う。条件の適用時点は次のとおりとする。

- 商品を最初に追加した時点の単価・税率・適用可能な会員値引き条件を商品行に保持する。同じ商品の追加・数量変更でも、この条件を維持する。
- 後から会員を指定した場合も、保持した値引き条件で特典を適用する。追加後に値引き期間が終了しても、その商品行には追加時点の条件を使う。
- 商品行を削除して再追加した場合は、再追加時点の条件を使う。
- 購入確定・保存再試行では、保持した条件で計算・保存する。

<a id="r-topic-10"></a>

#### 計算順序

1. 値引きは商品1個単位で計算する。割合値引き額は「税抜単価×値引き率」の1円未満を切り捨てる。
2. 同じ商品に複数の値引きが該当する場合、値引き額が最大の1件だけを適用する。
3. 値引き後単価は「税抜単価−値引き額」とし、0円を下限とする。商品行の小計は「値引き後単価×数量」とする。
4. 同じ税率の商品行の小計を合算し、その合算額に税率を掛けて、税額の1円未満を切り捨てる。
5. 税抜合計は値引き後の商品行の小計の合計、税込合計は税抜合計に税率別の税額を加えた額とする。

<a id="sec-3-3"></a>

### 3.3 取引保存・履歴

| 出典ID | 要件 |
|---|---|
| F19・F20 | 購入確定操作により、購入日時、商品、数量、購入金額、購入者、レジ担当者が後から分かる情報をDBへ保存する。会員なしの取引も保存できる。 |
| F21・F22 | 購入時単価・売上金額を取引に保存し、商品マスタの単価変更後も保持する。これに加え、商品マスタの単価変更履歴を保持する（U03）。購入確定時のデータと、値引き適用・単価変更の履歴が失われないようにする。 |

商品が0件の購入は認めない。空カートでは購入確定ボタンを無効にし、APIへの直接送信も拒否して取引を保存しない。商品が1件以上あり、値引きによって合計が0円となる場合は購入できる（F19・T01）。

保存結果に応じて次のように動作する（T02）。

| 保存結果 | 動作 |
|---|---|
| 保存成功を確認できた | 購入完了を表示する。 |
| 保存されていないと確実に確認できた | エラーと購入内容を保持し、「そのまま再試行」「内容を修正する」を選べる。修正は明示操作で編集へ戻る。 |
| 保存結果が分からない | 「保存結果を確認できません」と表示し、購入内容を保持する。同じ取引として再確認・再試行する。 |

- 「未保存を確実に確認」とは、保存されておらず、先の保存処理が後から成功する可能性もなくなった状態をいう。検索で見つからないだけでは、この状態としない。
- 未保存確認後に「内容を修正する」を選んだ場合、購入リストと会員情報を保持し、数量変更・商品追加・削除・会員指定を行える。既存の商品行は[3.2](機能・非機能要件.md#sec-3-2)の追加時条件を維持する。修正後は再度購入確定でき、修正前の要求と混在して古い内容や二重の取引が保存されないこと。識別・制御方式は設計で定める。
- 保存処理中・結果不明の間は、購入内容の変更と次取引への移行を止める。
- 再試行では同じ取引を識別できる情報を使う。既に保存済みなら、その購入結果を返して二重保存しない。
- 購入ボタンの連打でも、同じ取引を二重保存しない。

<a id="sec-3-4"></a>

### 3.4 再読込・ブラウザ終了後の復帰

- 同じ端末・ブラウザで、サーバーが受け付けた購入内容・取引状態を同じ担当者が復元して続行できる。
- 別端末への引継ぎは含めない。
- レジでは同じブラウザの通常モードを使用する。
- プライベート／シークレットモードは動作保証対象外とし、専用検知機能は作らない。
- Cookie消失時は通常の停止・手動確認を適用する。

| 中断前の状態 | 復帰動作 |
|---|---|
| 商品登録・編集中 | 登録済みの商品・数量・会員・商品追加時の条件を復元する |
| 会員確認待ち | 未確定を維持し、確認成功または非会員選択まで購入不可（[3.1](#sec-3-1)） |
| 購入確定送信後 | 同じ取引の結果を確認し、[3.3](#sec-3-3)の状態別動作に従う。結果不明の間は編集・次取引不可 |
| 保存済み・結果表示中 | 保存済みの結果を表示する |
| 次取引移行後 | 空カート・会員未指定で開始する |

- 復元対象は反映済みの商品・数量・会員・商品行の保持条件・取引識別情報・状態。未送信の商品コード・会員ID、確定前の数量入力、選択行、カメラ映像は復元しない。
- 認証が有効なら元担当者として復帰し、期限切れなら[4.2](機能・非機能要件.md#sec-4-2)の再認証を求める。復帰・再認証だけでは購入を自動送信しない。
- 応答断の操作はサーバー反映を照合し、商品追加を無条件に再送しない。復帰確認の失敗を新規取引開始・未保存の根拠にしない。

<a id="r-topic-11"></a>

#### 通常復帰の期限

- 最後にサーバーへ反映された業務操作から24時間経過前まで復帰できる。
- 画面表示・結果照会では延長しない。
- 24時間は復帰期間であり、DB削除期限ではない。

<a id="r-topic-36"></a>

#### 手動確認後の復帰

- 本人が開発・運用担当者として対象と結果を確認し、復帰を許可した時刻から改めて24時間復帰可能とする。
- 許可日時を別記録し、元の業務日時・購入日時・売上は変更しない。
- 以後の期限は最後の業務反映日時と復帰許可日時の新しい方から数える。
- 自動解除、レジ操作・照会・再認証による延長は行わない。
- 担当者認証・Cookie照合・購入状態による操作制限は維持する。

<a id="r-topic-13"></a>

#### 期限の起算とCookieの保持

| 項目 | 規則 |
|---|---|
| 起算更新 | 初回カート作成、商品・数量・会員・購入状態・次取引の変更がDBで確定した時刻。サーバー側の時刻を使う |
| 更新しない操作 | 画面表示・照会・ログイン・再認証・拒否された更新・処理済み要求の再送 |
| 復帰Cookie | 30日保持し、ブラウザ終了後も残す。正常な業務更新時に同じ識別子の保持期限を更新する。Cookieが残っていても通常復帰24時間は延長しない |

Cookieの期限更新はブラウザが応答を受け取った場合に反映される。DBの業務反映・復帰期限とは別管理とし、Cookie消失・復帰期限切れの停止条件は維持する。

<a id="r-topic-14"></a>

#### 復帰できない場合

| 状況 | 必要な動作 |
|---|---|
| 復帰期限切れ／Cookie消失・無効 | 理由を表示して停止し、本人が開発・運用担当者として手動確認する |
| 保存結果不明 | 結果を確認できるまで新しい購入を始めない |
| 停止中 | レジ操作だけでは復帰・新規購入できない。担当者認証だけで元取引を推測しない。自動取消・自動削除をせず、購入内容・取引識別情報・操作記録を調査用に保持する |

<a id="r-topic-15"></a>

#### 初回利用の識別

- サーバー側にレジ1台の利用開始記録を保持し、取引終了でもリセットしない。

| 利用開始記録・Cookie | 動作 |
|---|---|
| 未開始 | 担当者認証後に初回開始し、有効なCookieの受取確認後に商品登録できる |
| 開始済み・有効Cookie | 認証と復帰条件に従って利用する |
| 開始済み・Cookieなし／無効 | 継続中取引がなくても停止し、手動確認する。画面・APIから新しい購入を始められない |
| 初回のCookie受渡し不明 | 商品登録を開始せず、初回開始を無条件に繰り返さず手動確認する |

<a id="r-topic-16"></a>

#### DB記録の保持

- 演習中は途中カート・操作記録・売上・履歴を保持し、自動削除しない。
- 復帰期限切れ・Cookie消失でも削除しない。
- 演習終了後の削除は対象を確認して別途実施し、削除機能・定期削除処理は作らない。
- 記録増加を受容し、復帰・再送と削除の競合を避ける。

レジ担当者だけでは例外停止を解除できない制約は受容済み。専用管理画面は前提にしない。初期設定、排他、Cookie発行・照合、手動確認・再開手順は設計で具体化する（[第6章](対応と残課題.md#sec-6)）。

<a id="sec-3-5"></a>

### 3.5 複数タブからの操作

同じレジを複数タブで開いた場合は「別タブでも開いています。操作するタブを1つにしてください」と警告する。操作できるタブを厳密に1つに固定する方式は採用しない。

- サーバーは、古い状態を基にした変更を拒否し、最新状態の再取得を求める。
- 同じ取引はどちらのタブから購入確定しても二重保存しない。
- 警告が操作を防止することには依存しない。
- 複数タブで操作すると更新拒否・読み直しが発生する制約を受容する。
- 認証、会員確認待ち、保存処理中・結果不明など既存の操作制限は各タブにも適用する。

<a id="sec-3-6"></a>

### 3.6 入力・金額・日時の境界

関連：F01・F04〜F09・F16〜F22・F25・T01。手入力・読取・API・マスタ準備に同じ境界を適用する。

| 対象 | 規則 |
|---|---|
| 商品コード・会員ID・担当者ID | 1〜32文字の半角英数字・ハイフン・アンダースコア。先頭ゼロを保持し、大小文字を区別。空白・全角は自動変換せず拒否。会員未指定はID入力と区別する |
| 金額 | 単価・定額値引き・集計額は0〜999,999,999,999円の整数。超過する更新・保存は拒否し、部分反映しない |
| 税率・割合値引き | 0〜100％、0.01％刻み。範囲外・精度超過は丸めず拒否 |
| 日時・適用期間 | 保存はUTC、表示・期間設定は日本時間。開始時刻を含み終了時刻を含まない。例：9月30日までなら終了は10月1日0時。購入日時は売上書込処理で取得し、保存済み取引の再送で変更しない |
| 同額値引き | 最大候補額が同じなら条件ID昇順の最初の1件。優先順位設定機能は追加しない |

追加済み行の条件保持は[3.2](機能・非機能要件.md#sec-3-2)を維持する。採用形式は商品＝EAN-13／EAN-8（JAN）とCode 128、会員＝Code 128とする。QR等は対象外。読取後も同じコード形式を適用し、先頭ゼロ・大小文字を保持する。対象端末でのカメラ読取の動作確認は未実施。確認対象と期待結果は[5.1](受入条件_現行.md#sec-5-1)に定める。


<a id="sec-4"></a>

## 4. 非機能要件

<a id="sec-4-1"></a>

### 4.1 性能・稼働

| 出典ID | 要件 |
|---|---|
| N01・T03 | 営業時間内は同程度の応答速度で動作し、久しぶりのアクセス時だけ極端に遅くなる挙動を避ける。商品検索・会員照会・購入確定は、通常時も30分間アプリへアクセスしなかった後の最初の操作も、操作開始から結果表示まで2秒以内とする。購入確定はDB保存成功の表示までを測る。カメラのバーコード認識時間は含めない。 |
| N02 | 処理のたびに実行環境がゼロから立ち上がる構成は避ける。DB接続をある程度維持する運用が望ましい。後者は推奨であり必須条件に強めない。 |

<a id="sec-4-2"></a>

### 4.2 セキュリティ

以下をF01・F02の認証保護として適用する（T04）。

- パスワードを平文保存せず、パスワード保存用の方式でハッシュ化する。ログにも出力しない。
- 未ログインの利用者はPOS画面を利用できない。APIへの直接アクセスでも、商品・会員情報の取得や取引保存を拒否する。
- 認証失敗時はIDとパスワードのどちらが誤りかを区別せず、「担当者IDまたはパスワードが正しくありません」と表示する。

<a id="r-topic-17"></a>

#### ログイン試行制限

同じ担当者IDで直近10分間に5回の資格情報照合失敗があれば、5回目の失敗時刻から10分間、ログイン・再認証を制限する。制限中は正しいパスワードでもログインさせず、追加試行で制限を延長しない。期限到達時に自動解除し、専用解除画面は作らない。既存の有効なログイン状態・カート・売上は変更しない。担当者IDの存在を明かさず、認証失敗の表示を共通にする。DB不通・通信障害をパスワード失敗として数えない。

<a id="r-topic-45"></a>

#### 取引中の再認証

購入途中のログイン期限切れは、通常のログインと区別して次のように扱う。同じ画面での再開に加え、[3.4](#sec-3-4)の再読込・ブラウザ終了後の復帰でも適用する。

- 商品・数量・会員・商品追加時の条件と取引の識別情報を保持し、POSの業務操作を止めて再認証を求める。
- 同じ担当者の再認証に成功したら元の取引へ戻る。編集中なら編集を再開するが、会員確認待ちなど元の操作制限は引き継ぐ。
- 保存処理中・結果不明だった場合は、再認証後も保存結果が分かるまで編集と次取引への移行を禁止する。同じ取引の結果を再確認し、保存済みなら購入結果を表示する。未保存を確実に確認できた場合は「そのまま再試行／内容を修正する」を選べる。
- 再認証の成功だけで購入保存を自動送信しない。期限切れや再認証の失敗を未保存の証拠としない。
- 誤った認証情報には共通の認証エラーを表示し、内容を保持して再入力を待つ。別の担当者では当該取引を再開できず、元の担当者での再認証を求める。元の担当者が再認証できない間は続行できない。

<a id="r-topic-43"></a>

#### ログイン期限・認証応答不明

- ログイン・再認証成功から8時間固定。8時間経過時に失効し、操作による自動延長・無操作による短縮は行わない。1台・有人レジの演習を前提に、離席中も期限までは認証が続く制約を受容する。
- 認証応答が途切れたらサーバーへ状態を照会する。有効なら対象・担当者を照合して復帰、未認証なら再入力、照会不能なら操作停止・内容保持。認証照会だけで購入を送信しない。
- 認証8時間と通常復帰24時間（[3.4](#sec-3-4)）は別管理。再認証だけで復帰期限を延長したり、期限切れ・Cookie消失時の手動確認を省いたりしない。

<a id="r-topic-44"></a>

#### 認証Cookieの保護・切替

- 認証CookieはHTTPSだけで送信し、JavaScriptから読み取れない設定とする。
- 他サイトからの操作はCookie制限と送信元・専用ヘッダーの検証で防ぐ。
- 再認証成功時に新しい認証Cookieへ切り替え、旧認証を無効化する。
- 遅延・応答順逆転で古いCookieとなった場合は、内容を保持して状態照会・再認証する。
- この通信競合時の再認証を受容し、8時間・24時間の期限は変更しない。

パスワードのハッシュ方式と認証状態の管理方式は、上記の要件を満たすよう設計で具体化する。

<a id="sec-4-3"></a>

### 4.3 運用・データ保護

DBはAzure標準の自動バックアップを7日、診断用アプリログを7日保持する。途中カート・操作記録・売上・価格履歴は[3.4](機能・非機能要件.md#sec-3-4)どおり演習中保持し、診断ログの期限で削除しない。

- 安全な続行を判断できない異常では対象操作を停止し、本人がログ・DBを確認する。
- 未登録商品等の通常の入力エラーは既定の再入力・修正手順を維持する。
- 専用監視画面・外部通知連携は追加しない。
- ログにパスワード・Cookie・秘密値・会員属性・要求本文を記録せず、本人だけが閲覧できるようにする。
- 復元・配置変更の実行は対象と影響を確認して別途許可し、バックアップの存在だけで復元成功・データ無損失を保証しない。
