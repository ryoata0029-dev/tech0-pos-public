|---|---|---|---|
| 非会員→Bの照会中 | 実受付COMMIT後PENDING、実lookup完了後・反映前を私有gateで保留 | 570円参考表示、商品追加／数量／削除／購入は禁止、売上増加なし | B3の新MEMBER_0選択を先に確定 |
| A→Bの照会中 | 同じ実保留、旧Aの537円を保持 | 旧Aを適用中と確定表示しない。上と同じ商品制限 | B3の新非会員選択を先に確定 |
| 非会員→不存在 | SET_MEMBER REJECTED/MEMBER_NOT_FOUND・PENDING | 同画面は会員操作有効、商品禁止。別タブも待ち制限。参考570円 | 状態再確認の追加要求なしに再入力で会員成功 |
| A→不存在 | 同じ不存在確定、参考537円 | 同画面は会員操作有効、商品禁止。旧Aへ自動復帰しない | 追加状態再確認なしに非会員570円 |
| 非会員→照会不能 | 実受付COMMIT後3秒503・PENDING/PREPARED | 未確認会員・参考570円、送信中／503後は同画面停止。別タブ取得後も商品禁止 | 正規の明示GET後に再照会で537円 |
| A→照会不能 | 同じ503、参考537円 | 旧Aを確定表示しない。同じ停止・待ち制限 | 明示GET後に非会員570円 |

商品ありの各6条件で、最新cart_id／version・存在するline_id・新operation_idを使う正常形式の追加POST、数量PATCH、削除DELETE、購入POSTを直接要求する。期待はすべて409 STATE_CONFLICT。古い版／不正入力による拒否を成功に数えない。最大24拒否要求だが、実施した条件・要求だけを報告する。API前後と別接続DBでcart／line／版／操作／売上等が不変。別タブで行未選択なら数量／削除ボタンは出ないため、行選択自体が無効で到達不能だった証拠と、同画面の選択済み数量／削除無効を分ける。

会員GET成功・resume／cart GETだけでPENDINGを解除せず、版・旧参考額・売上が不変であることを照会中／不存在／不能の3条件で記録する。GET成功をSET_MEMBER成功へ読み替えない。

保留中の別タブ／4直接要求の採取が10秒以内に終わらない場合、B2の待ち制限とサーバー旧処理不反映までを記録して正規照合・選択で復帰する。B3のブラウザ到達確認は、同じ前提を正常操作で作り直した別の保留要求・新tagで短時間実施する。長時間の同じgateを使って実旧応答到達を合格にしない。

### B3 旧照会を新選択の後に完了

実lookup後・反映前の旧MEMBER_1を保留している間に、正規APIで別のMEMBER_0成功または非会員を明示選択し、APPLIED・新会員／金額／版を確認してから旧処理を私有releaseで再開する。Cookieを読取・移植せず、通常Cookie送信とOrigin検査を通す。新選択は通常POS別タブ、または対象限定の通常API検証画面を使い、どちらを実施したか明記する。公開障害制御API・偽の成功応答・DB状態名の注入は行わない。

旧処理はREJECTED/MEMBER_LOOKUP_SUPERSEDED、新選択後のID／金額／行条件を維持し売上増加0。実ブラウザの旧応答も確認する場合は、中継10秒／ブラウザ15秒のtimeout前に解放する。受付→lookup保留→新選択APPLIED→解放→旧処理完了→旧応答DOM→明示GETの時刻・元操作IDを残す。旧拒否による停止／参考表示を許可解除と取り違えず、明示照合後だけ新状態を表示する。

解放が10秒以降なら「サーバー旧処理不反映」のみ。HTTP本体・受信時刻を保存できなければ、秒数はサーバー処理完了までとし、DOM拒否文言との照合根拠を記す。実旧拒否応答と、古いAPPLIED成功応答を返す試験を混同しない。

## 6. 続くまとまりC：重い未網羅条件の具体化

この節は後続計画で、A0/A/Bの実行範囲に自動追加しない。現行共通ツールにはStorage障害・認証時刻制御・next成功応答の保留方式が揃っていない。実行担当が対象・方式・戻し方をレビュー可能にしてから進める。

| 優先候補 | 必要な前提・方式と判定 |
|---|---|
| TC-24 先へ進んだ後の旧next応答 | C1保存→実next(C1→C2)成功応答だけ保留→別タブでC2取引を保存／nextしてC3へ→旧応答を解放。旧new_cart_idはC2のまま、REGISTER／resumeはC3、元画面はC3へ収束。操作GETのcartは旧C1と区別。現行のdrop機能だけでは保留成功応答を後で返す試験はできない。10秒以内の成立性と正規同要求／別IDの照合を準備する。 |
| TC-20 Storage異常・複数記録 | 実Chromeの書込不能では購入POST未送信を要求到達ログ／DBで確認。読取不能・破損では停止。専用オリジン・架空の補助記録だけを制御し、Cookieや会員情報は操作・保存しない。原要求を持つケース、補助記録のみの復帰、PENDING重複PREPARED／REJECTED、R応答断、同／別カート記録の適用版未満／同値／超過、現在SAVING／SAVEDと古い確認応答を個別判定。[詳細条件](../tests/API・DB詳細.md#review-races)どおりの限定除去を確認する。停止対象から正常に戻せない場合は記録保持のまま環境を止め、無関係な記録を削除して続行しない。 |
| TC-28 状態別再認証 | 6状態を通常API遷移／実障害位置で作り、認証だけ失効、復帰24hは有効を保つ。各状態で誤PW→別担当者→元担当者、画面継続と再読込を別判定。元内容・条件・保存結果保持、他担当者拒否、再認証による自動購入なし。別担当者をクライアントが送信前拒否した場合はUI判定だけで、API403の直接確認は別。8h実待機か、隔離領域限定のauth期限／判定時刻制御を具体化する。単なる偽401注入で実失効・Cookie切替確認を代用しない。誤認証の合算5回制限を混在させず、各状態の新認証開始・失敗履歴を記録する。 |
| TC-18/19、TC-06/07等 | 通知欠落・更新応答断／sync両順、計算表・マスタ競合は上記監査表に残す。A/B成功によって網羅した扱いにしない。 |

ひとつの新規Mac環境で正常nextによってカートを順に進めることは可能。ただしStorage破損や未解決要求で正規の継続が不能なら、その領域は停止・保持し、後続用の別隔離領域を準備する。ひとつの環境で完走するために不明状態を消さない。TC-28等の新しい時刻／Storage故障制御はA/Bから分離して影響範囲を確定する。
