## 2. 実施条件・判定方法


### 共通準備

- 実装版、対象環境、実行日時、使用データの版を記録する。MacBook Airのモデル・macOS版、iPhone 15のiOS版、各Chrome版を記録し、通常モードで使用する。画面・カメラ・Cookie・復帰は両端末で個別に確認する。
- 架空の担当者A／B、会員A／B、未登録コード、正常な会員6属性を用意する。商品は103円・税率10％、別商品2件を各107円・税率8％とし、10％引き・20円引き・120円引きはケースごとに適用条件を切り替える。通常ケースは特記がなければ認証済み・空カート・会員未指定・期限内から開始する。
- 計算・入力境界は単体確認、API・原子性・競合は実DBとの結合確認、業務の流れは画面からの確認で実施する。実機・Azure・復元が必要な確認を模擬結果で代用しない。
- 初期データ投入、時刻制御、通信遮断、処理の一時停止、DB障害の注入は、許可された検証環境で対象・手順・戻し方を確定してから行う。保存前後の停止位置を識別できない場合は、そのケースを実施不能とする。
- ケース間で前のカート・会員・認証・マスタ変更・障害設定を持ち越さない。正常に次取引へ進めるか、承認された検証用初期化手順を使う。結果不明の取引を新規取引で置き換えず、記録の削除を自動的な後片付けにしない。

### 初期状態の準備と開始条件

準備する状態は次の3種類とする。各ケースの「前提・データ」が共通状態より優先する。確認対象の操作そのものは準備で済ませず、試験開始後に実施する。例：ログイン試験はログイン前、初回confirm試験はCOOKIE_PENDINGで開始する。以下は準備の仕様であり、投入SQL・初期化処理・障害制御コードは実装工程で作る。

| 初期状態 | 準備するデータ・操作順 | 試験開始を認める確認条件 |
|---|---|---|
| 初回利用前 | 他の試験記録と分離した検証データ領域へ、担当者A／B・会員A／B・税率・商品・初回価格履歴を準備。REGISTER=1を未開始で用意し、通常モードのブラウザを対応付ける前の状態にする | REGISTERが1件・UNSTARTED、保守停止なし、有効context／cart／session参照なし。認証・復帰Cookieと購入不明の補助記録なし。カート・操作・売上・明細・税集計なし。誤認証の失敗記録・制限なし。必要な基準データが揃い、不存在用IDは未登録 |
| 通常操作開始前 | 初回利用前→Aで通常ログイン→start→Cookie受取→confirm→初回カート作成。画面試験では画面の通常操作を通し、API試験では同じ公開APIの順序で準備する | 認証有効、REGISTER=READY、復帰Cookieが同じブラウザ・担当者・継続カートに一致。認証8時間・復帰24時間の期限内。カートEDITING、空、会員UNSPECIFIED、合計0。会員・購入の処理待ちなし、補助記録なし、当該カートの売上なし。カメラ停止、送信中要求・障害制御なし |
| 特定状態から開始 | 通常操作開始前を起点に、対象ケースの商品・値引き条件を準備して操作を進め、下表の到達点で止める。直接DBへ状態名を書いて通常遷移の代用にしない | 対象cart_id・operation_id・version、到達時刻、画面状態とDB状態、保持条件を照合。必要な停止・遮断が指定位置で有効であり、想定外の処理が進んでいない。値引き・期限の起算はケースの条件と一致 |

特定状態の作成順（3章の前提がこれより細かい場合はそちらを使う）：

| 作る状態 | 到達させる操作・停止位置 | 開始前に確認すること |
|---|---|---|
| 商品あり・編集中 | 対象の値引き候補と有効期間を用意してから商品追加→必要な数量・会員を指定 | EDITING、行と合計が期待値、追加時の保持条件が一致。設定変更後の保持を調べるケースだけ追加後にマスタを変更 |
| 会員確認待ち | 会員変更を開始し、確認待ちのDB確定後・照会完了前で停止。不在／確認不能を前提にする場合はその結果まで進める | member_state=PENDING、候補IDと操作が一致、商品編集・購入不可。旧合計は参考表示 |
| 保存処理中 | 購入要求を送信し、受付コミット後・売上TX開始前で停止 | CART=SAVING、購入操作PREPARED、受付版が一致、当該売上・明細・税は0件。操作制限が有効 |
| 保存結果不明 | ①要求を未到着で保持、②受付後に応答を遮断、③売上コミット後に応答だけ遮断、をケースごとに別実施。結果照会で解消する前に止める | 画面は結果不明・編集／次取引不可。②では受付後・売上TX開始前の処理停止も併用する。DBは①EDITING、②SAVING、③SAVEDとなり得るためUNKNOWNをDBの状態名として作らない。試験側の読取で到達点を確認し、その結果を画面へ注入しない |
| 未保存確定 | 売上なしの購入不明状態からresolve-purchaseを確定する | CART=UNSAVED、確認操作APPLIED、当該売上なし。旧受付操作がある場合は終了済み、未到着要求も旧版で拒否できる。編集再開・再購入はまだ行わない |
| 保存済み・結果未終了 | 通常の購入を成功させ、結果表示を閉じる前で停止する | CART=SAVED、購入・全明細・税集計が確定、表示内容と一致、nextは未実行 |
| 認証・復帰期限の境界 | 先に対象カート状態を通常操作で作り、起算を記録してから試験用の判定時刻を設定する | 2章の直前／到達／直後と一致。認証だけを失効させる試験では復帰24時間を有効に保つ等、対象外の停止条件を混在させない |

**ケース間の切替**：通常操作で購入完了→nextへ進めた場合は、通常操作開始前と同じ条件を確認して次ケースに使用できる。ただしカートの初期版1や履歴0件を条件とする試験は、新しい初回用データ領域で行う。初回試験のやり直しをCookie削除だけで済ませたり、開始済みREGISTERを未開始へ戻したりしない。編集中・結果不明等の未完了対象は記録を保持し、正規の復帰・完了ができなければ当該領域を停止したまま別の隔離領域で準備する。これは本番の新規取引による回避を許すものではない。

両端末の確認は端末ごとに初回用データ領域とブラウザ状態を分離して同じ条件を作る。1店舗・レジ1台という各試験内の条件を維持し、別端末引継ぎや2台同時レジの試験に変えない。通常遷移で作れない不整合データはTC-13の隔離条件でのみ用意する。準備に失敗した場合は本試験を始めず、原因と未実施範囲を記録する。データ領域の作成・切替方法と実行権限は実装・環境準備時に確定する。

### 実装前に定める共通方式

以下は既存の受入条件を再現するための試験方式。要件・設計の変更や、ツール導入・実行の許可を意味しない。ツール名・コマンド・接続先は実装時に具体化する。

| 項目 | 今回定める方式 |
|---|---|
| 実施順 | ①計算・入力境界→②API・DB・認証→③保存・競合・復帰→④両端末の業務・カメラ→⑤Azure性能・運用。失敗原因を小さい範囲で特定するための基本順であり、独立したケースは先行可。最後に本人がTC-01の会員／非会員フローを両端末で確認する |
| データの分離 | 正常データを基準にし、不正試験は1項目だけ変更する。不存在・境界・競合用データは別条件として識別する。実行ごとに利用したIDと条件を記録し、連番や既存DBの内容を推測しない |
| API入力・応答 | 正常要求を操作ごとに1つ定義し、必須欠落・null・型違い・未定義項目を1つずつ変える。正当なnullや本文なしを不正扱いしない。型・HTTP・codeはOpenAPI、状態と副作用は詳細設計で判定する。全入力値の無差別な組合せは作らず、列挙済み境界と状態の相互作用を確認する |
| 時間境界 | DBのDATETIME(6)に合わせ、判定時刻Tの直前T−1μs／T／直後T＋1μsで論理判定を確認する。期間の開始はTから有効、終了・認証8時間・復帰24時間はTで無効、ログイン制限はTで解除。10分窓の下端ちょうどは対象外。サーバー時刻を与えられる試験経路で検証し、端末時計変更や長時間待機で厳密境界を代用しない。実DBとの時刻取得・精度・UTC連携は別途結合確認する |
| 障害・競合の再現 | 通信断は「要求未到着」「ブラウザへの応答喪失」「MySQL→FastAPIのCOMMIT応答喪失」を分ける。最後は受付TXと売上TXを別実施し、DB確定済みでもアプリがCOMMIT成功を確認できない位置を識別する（[TC-16詳細](API・DB詳細.md#tc16-fault)）。処理の到達を確認して一時停止し、他方の操作を完了させてから解除する。偶然の同時クリックや一定時間のsleepだけで順序を成立させない。試験専用の制御手段は検証環境内に限定し、公開APIに障害注入機能を追加しない |
| 証跡・戻し | ケースごとに①開始前の対象・状態、②実際の入力と処理順、③表示／応答、④確定後のDB差分を必要な範囲で残す。購入はcart_idでPURCHASE件数と明細・税・操作状態を照合。障害解除後も結果確認を先に行い、未確定DMLはROLLBACK、確定済みは保持する。DDL・DB全体の自動巻戻しは行わない |

共通データの具体値（投入ファイル・パスワード・バーコード画像は未作成）：

| 対象 | 値・条件 |
|---|---|
| 担当者・会員 | 担当者 `STAFF_A`／`STAFF_B`。会員 `MEM_A`／`MEM_B`、氏名「試験会員A／B」、電話「TEST_PHONE_A／B」、住所「試験用住所A／B」、性別「試験値A／B」、年齢0／30。電話等へ既存仕様にない形式制限を追加しない。パスワードは実行準備時に生成し本書や証跡へ記載しない |
| 計算用商品 | `P103`＝103円・税10％、`P107_A`／`P107_B`＝各107円・税8％。全て値引きなしを基準とし、TC-06の各条件でP103の候補を入れ替える。候補を累積させない |
| 不存在・文字区別 | `NO_PRODUCT`／`NO_MEMBER`は未登録を確認して使用。`001Ab`／`001ab`は別商品として登録し、Code 128・手入力・APIで別商品と判定する。境界は `A`、`A`32個、`A`33個、空文字、` A`、`A `、`A`＋改行、全角`Ａ`を使用 |
| JAN読取 | EAN-13は `2000000000015`、EAN-8は `20000011`。両方を検証DBへ別商品として登録する。検証専用ラベルと明示し、実商品のコード・実取引データを流用しない。両コードとCode 128の画像生成・印刷品質は実機準備時に確認する |
| 保存の基準データ | TC-06の混在税率条件を使用。保存成功時は売上1件・明細3件・税集計2件、税抜493円・税込537円。売上TX失敗時は3表とも対象cart_idの行が0件。受付済みCART／CART_OPERATIONは残り得るため、売上0件だけで編集可と判定しない |

### 記載・記録・判定

以下のTC番号は本書で新規採番する。1行に列挙した値・状態・順序はすべて確認し、実行記録では `TC-xx／条件名／端末` で個別に結果を残す。行数を実行件数や網羅率とみなさない。共通の前提・データは上記を使い、各行には差分を書く。 TC-03は初回指定／会員変更の双方で成功・不存在・確認不能と解除手段を確認し、各待ち状態で同画面／別タブ／直接APIの追加・数量変更・削除・購入の拒否を確認する。TC-21は列挙した全状態×再読込／終了再起動×両端末、TC-28は列挙した全状態×元担当者／誤認証／別担当者を省略しない。他の独立した入力境界は1項目ずつ変え、根拠のない全組合せ試験は追加しない。

<a id="shared-evidence"></a>

同一の前提・入力・期待結果を、同じ実装版・環境で確認する場合は、1回の実行と証跡を複数のケースIDへ対応付けてよい。各IDの条件別判定は残し、同じ実行ID・証跡への参照を記録する。成功した実行回数を重複計上しない。

| 共有候補 | 同一ならまとめる条件 |
|---|---|
| TC-11／25 | 未認証・期限切れ・対象の所有権による拒否 |
| TC-11／29 | Origin・X-POS-Requestの検査 |
| TC-11／12 | 同一要求再送・古い版・同IDの異内容 |
| TC-10／11 | 空カート購入の直接API拒否 |

適用APIや状態が異なる条件、画面操作と直接API、端末・環境が異なる確認は別実施とする。共有は必須条件の省略を認めるものではない。

実行記録は「ケースID・条件／実装版・環境／実施日／合格・不合格・未実施・実施不能／実結果・証跡／不具合・不能理由」を持たせる。画面、秘匿済みのAPI応答、対象を限定したDB読取結果から必要な証跡を残す。認証値・実在顧客情報は記録しない。DB確認は[設計確認SQL](../../設計確認.sql)を必要な対象へ限定し、空データで異常0件だけを合格にしない。

- **開始**：対象の実装と環境が用意され、関連する4章の手順・成立性・実行条件を満たしたケースから実施する。
- **中断・再開**：保存結果や対象の特定不能、データ不整合、予定外の環境影響があれば関連試験を止める。原因・対象状態を確認し、必要な修正と復帰後に再開する。
- **合否**：手順中と終了時の期待結果をすべて満たして合格。実施不能・未実施は合格に含めない。修正後は失敗条件と影響する関連ケースを再試験する。
- **完了**：現行受入条件の必須確認が合格し、欠陥探索の独立レビューと本人の主要業務フロー確認を終え、本人が受入を判断する。必須条件が未実施・実施不能・不合格なら、その受入判断を保留する。条件付き受入は本人が対象・影響・残作業を確認して別途判断し、試験結果を合格へ書き換えない。
