## 適用順と確認

1. 対象サブスクリプション・専用リソースグループ・リソース名・管理者・通常DB利用者・費用上限・既存資源への影響を設定票へ記録。テンプレートは既存app settingsを置換し得るため、既存環境へ無確認で適用しない。
2. 共有planと無効な両アプリを作る段階、DB作成段階、アプリ配置段階を分けて許可。初回アプリ作成後に送信元IP群を読み、front→backend、backend→DBの許可値を作る。`check_config.py 設定票.json`で事前確認し、テンプレートへの転記値と再照合する。全Azure許可（0.0.0.0）、範囲／全IP許可は使わない。本人のDB保守IPは作業時だけ追加・撤回。
3. 接続先を固定し、TLS証明書・ホスト名を検証。管理者資格でDDL／架空データ／権限を準備し、通常アプリ設定には管理者を入れない。現行[M3実DB手順](M3_DB実行手順.md)と同じ正本DDL／16表を照合。REGISTERを保守停止状態にする。
4. Linuxの隔離ビルド環境で固定版Node／Pythonを用い、通常の`make check`・`make build`を通す。性能記録を取得する配備だけはビルド前に`NEXT_PUBLIC_POS_MEASUREMENTS=1`を指定する（公開ビルド時に埋め込まれる値で、runtime変更だけでは変わらない）。次に`python3 tools/operations/prepare_deployment.py .deployment/RELEASE_ID`で準備。backend配備ルートでPython3.13のvenvを作り、`python -m pip install --require-hashes --only-binary=:all: -r requirements.lock`。信頼する公開CAを別途配置し、環境のCAパスと照合。Linuxでの固定hash適合は未確認。
5. 配備前にファイル一覧を確認し、検証環境・秘密値・DB・不要記録を除外。zipのルートは各appのserver.js／app/とする。承認済み対象だけへ配備し、必要設定を投入して起動。frontendの計測フラグはビルドとの一致を確認。秘密パラメーターは保護したファイル／安全な入力で渡し、履歴・Git・出力へ残さない。
6. FastAPIが直接利用者から拒否され、正しい中継秘密値とOriginだけ通ること、Cookie保護属性、通常DB権限、healthがDBや期限を変えないこと、1 worker・pool5/overflow0/recycle300を確認。ネットワーク設定変更のたびにIP群を再照合。
7. **両LinuxアプリのPortalでApplication loggingをFile System・7日・100MBに設定して読取確認。** ARMのapplicationLogs.fileSystemにはlevelしかなく、httpLogsの保持項目で代用していない。設定票に保存し、架空の機密入力の非漏洩、7日分の取得／期限処理、容量・再起動・ログ欠落を別途検証。追加監視サービス・外部送信・独自削除ジョブなし。
8. 同じ担当者・カート・商品条件で主要フローと下記性能・復元を確認。失敗／不整合は停止を維持。本人が主要フローと対象段階の結果を確認してから運用開始。

## 手動停止・復帰と最小権限

[manual-recovery.sql](../../tools/operations/manual-recovery.sql)は既存DBクライアントで選択した節だけ実行する作業票。全体をsourceせず、既定ROLLBACKのまま対象・版・更新件数を確認する。専用復旧API／自動復旧スクリプトではない。Aの停止はDB確定後、両アプリ停止と実行中DB処理の解消まで確認。Bで元の対応、全明細・税・候補条件を照合。Cは保存受付中・売上なし、Dは会員PENDING、Eは他の整合した状態。各分岐で旧要求を版で無効化する。売上・金額・購入日時・last_business_atは変更しない。不整合、版上限、複数候補、DB不通なら解除不可。

作業権限は担当利用者へ一時付与し、必要分岐だけ選ぶ。SELECTは対象特定に必要な表。UPDATE候補はREGISTER(maintenance_hold,active_session_hash)、AUTH_SESSION(revoked_at)、BROWSER_CONTEXT(token_hash,manual_released_at)、CART(version,state,active_purchase_operation_id,purchase_prepared_version)、CART_OPERATION(status,result_code,applied_version,completed_at)。売上UPDATE／DELETE、全表UPDATE、DDL、通常ユーザーへの復旧権限は与えない。列単位GRANT／REVOKEは実DBのユーザー・host・DB名を安全に確定して実行し、SHOW GRANTSと対象外更新拒否を照合する。SQL文例：`GRANT UPDATE (maintenance_hold,active_session_hash) ON 対象DB.REGISTER TO 対象利用者`。識別の失効後は認証を安易に元へ戻さない。

Fの復帰識別修復はCookie消失／無効時だけ。本人が32バイト乱数を安全に生成し、同じ端末ChromeへSecure／HttpOnly／SameSite=Lax／Path=/／Domainなしで設定する。DBにはSHA256だけ渡す。値は記録・URL・本文・HAR・画面撮影へ残さない。旧セッション失効、同じcontext/cart/staff、manual_released_atから24時間、元のPENDING／保存済み状態、旧Cookie拒否を確認。初回COOKIE_PENDINGでカートなしも開始済みを保持し、解除後confirmを通してから初回カートを作る。

Gの解除前は保守停止のまま同じ担当者で再認証・GET照合。補助記録が残る場合は、解除後にアプリのresolve-purchaseを通し対応するAPPLIEDの版で対象分だけ消す。単なるGETや現在版を根拠にlocalStorageを削除しない。途中失敗は未確定TXをROLLBACKし停止継続。確定済みの変更は変更前状態・影響を確認して別の修正を判断する。

## 性能の記録

計測を有効にしたビルドでは、手入力の正常な商品検索・会員照会・購入確定の開始から、確定結果の表示後までを`window.__posMeasurements`に最大200件だけ保持する。カテゴリ・単調時刻・確認済みフラグのみで、コード・会員属性・価格・認証値・取引IDは記録しない。カメラ認識や結果不明を測定完了にしない。ブラウザ終了で消える。専用監視画面はない。

各Chrome実機で、操作ごと通常10回と**各操作の前に**30分無アクセス後1回を測る。同じ端末・回線・架空データ条件を記録する。API所要時間や平均値で代用しない。記録ファイルは次の形（samplesに66件が必要、これは形の例であり実測ではない）。

```json
{"environment":"AZURE","samples":[{"device":"MAC_CHROME","operation":"PRODUCT","mode":"NORMAL","start_ms":100,"display_ms":1100,"confirmed":true,"idle_ms":0,"no_access_confirmed":false,"conditions_id":"trial01"}]}
```

`backend/.venv/bin/python tools/operations/check_evidence.py performance 記録.json`。PURCHASEは保存済み表示だけconfirmed、会員はCONFIRMED／明示した非会員、商品は検索結果表示で確認。失敗応答・受付だけ・実測欠落は合格にしない。30分の無操作・無アクセス（別タブを含む）の証跡と端末版は本人が別記録する。ツールは記録値の整合・各回2秒を判定し、記録の真実性や実機受入は保証しない。

## 別サーバー復元と差分

本人の対象時刻・追加費用・実行許可を得てAzure標準復元を**新しいサーバー**へ行う。旧DBは保持。保守停止・両アプリ停止後に、旧DBと復元DBそれぞれを読取専用REPEATABLE READの1TXで16表の全列・主キー付き行として照合する。安全なクライアント内で型／NULL／正確なDECIMAL／UTC／JSONを同じ正規化にし、各行をSHA256へ変換。生行・秘密値・会員属性をこのツール／Gitへ渡さない。snapshot_at・consistent_read・tablesを記録：tablesは16表名それぞれに行digestの配列。ダイジェスト自体も取得先を保護し、コピーの保管期限を別管理する。

`backend/.venv/bin/python tools/operations/check_evidence.py restore 旧DB-manifest.json 復元DB-manifest.json`。exit0は全行digest一致、1は差分あり、2は欠落／不正／未確認。欠けた表を空配列で補わず、旧DBを読めなければ照合不能とする。復元点以降の売上・操作・価格履歴・途中カート・認証の差分を本人が解消するまで切替不可。manifest生成／正規化の一致は実検証事項。全16表一致だけでも旧認証失効・Cookie修復・起動確認・利用再開承認は別条件。データ損失をアプリのロールバックと扱わない。
