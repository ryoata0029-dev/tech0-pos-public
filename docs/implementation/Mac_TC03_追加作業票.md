## 順序と判定

1. 通常のUIログイン・開始・Cookie確認後、商品追加前の空カートで、初回／非会員からの指定とAからBへの変更を行う。成功・不存在・照会不能・再入力／再照会・非会員を確認。金額0、商品登録不可、旧IDへ自動復帰しないことをDBと照合する。
2. UIで3商品（103円×3、107円×1を2商品）を登録して非会員570円を確認。初回／非会員からの指定とAからB変更で同じ全分岐を確認。成功537円、非会員570円。旧額の参考表示・元明細保持、商品編集／購入停止、正常復帰後の解除を確認する。
3. 商品ありの確認中・不存在・不能それぞれで、通常の別タブに同じカートを表示し、商品追加／数量変更／削除／購入のUI停止を確認する。別タブに選択明細がなければ選択ボタン停止により数量／削除へ進めないことを記録する。
4. 同じ通常Chromeの認証で検証用API画面から、最新cart_id／version・新しいoperation_idの正常形式で商品追加／数量変更／削除／購入を直接要求。PENDING時の409 STATE_CONFLICTと、版・明細・金額・売上・操作記録に変更がないことを確認する。会員GET成功とカートGETだけでは待ちを解除しないことも確認する。
5. 会員受付の実COMMIT後にPENDINGを記録し、実際の会員照会が完了した後・反映前で旧要求を一時停止。新しい明示会員選択または非会員化を別タブから確定し、旧処理を再開する。旧照会をREJECTED/MEMBER_LOOKUP_SUPERSEDEDとし、新しいID・額・版・明細を上書きしないことを画面・DB・旧処理完了証跡で確認する。中継の10秒タイムアウト後のサーバー処理と、10秒以内に届く実旧応答の条件を区別する。

各下位条件の前に通常の非会員選択／会員成功で基準状態を作り、前提を観測する。1カートの会員指定・再入力を追跡するTC-03の一連試験であり、履歴0／版1の独立初回ケースとは区別する。空カートで有効な数量変更／削除の対象はないため、4操作の拒否は商品あり状態で確認する。購入成功は今回要求しない。

## 制御・記録・終了

障害はmac-tc03 profile内だけ。照会不能は実受付COMMIT後3秒で503。確認中／遅着は実会員照会の読取完了後、DB更新ロックを持たず最大600秒停止し、私有ファイルで再開する。公開する障害制御APIは追加しない。通常API／DBによる状態遷移を使い、PENDING等の状態名を直接DBへ注入しない。

検証用API画面はprofile限定HTTPSの`/__tc03`で提供し、通常のsame-origin認証・Origin／X-POS-Request・Next.js中継・FastAPI・DBを通す。Cookieを読取・表示・移植せず、認証・権限・証明書検証を維持する。操作は固定したTC-03要求（4拒否要求、読取、新しいMEMBER_0または非会員の明示選択）に限定し、秘密値・属性・認証ヘッダーは画面／証跡へ出さない。新選択はPENDING時にだけ送る。試験用ログイン資格情報／Cookieは承認済みCloudflare中継を通る。

UI／DB／要求と応答／指定した停止位置／実装版・hash・端末版を保存し、独立した欠陥探索レビューを行う。不合格・未実施を合格へ読み替えない。カメラ撮影、Code128、iPhone、Chrome全体終了、Azure、本番公開／デプロイ、commit／pushは含めない。終了時は今回のアプリ・トンネル・専用DBを停止し、DB／volume／証跡を保持する。戻す場合はprofile・試験画面・障害制御の今回限定差分のみをレビューして戻し、既存アプリ修正・旧記録を保持する。
