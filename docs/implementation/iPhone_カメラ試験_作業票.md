## 実行前の成立条件と役割

- 主担当がアプリ修正版を確定し、ソースhash・build ID・検査結果を記録する。並行するP2修正中のbuildを受入対象にしない。[M5修正](M5_カメラ確定エラー修正.md)と[会員不存在修正](Mac_TC03_不存在復帰_修正再検証結果.md)は自動検査／Mac手入力の証拠であり、実カメラ・iPhoneの合格ではない。
- 主担当が専用DB／volume／私有領域、公開URL、対象端末・担当者・カート、開始終了時刻を確定する。本票では対象資源名を未決のまま作成・起動しない。旧DB・Cookie・期限を流用、初期化、延長しない。
- 現行手順のDB3307、HTTPS8443／8444、共通のNext.js buildは他担当と競合する。主担当が環境の利用枠を割り当て、同時起動・build上書き・他担当のプロセス停止を防ぐ。MacとiPhoneの初回条件は対象DB／Cookieを分け、同一レジの二重開始にしない。
- MacBook Air・iPhone 15各1台のChrome通常モードを使用し、モデル・OS・Chrome版を今回取得する。過去のiPhone Inspector接続記録は現在の接続可能性を証明しない。
- 本人はiPhoneの接続・対象URL表示、許可ダイアログ、バーコードの物理提示、向き変更、キーボード表示、背景移行等を担当する。主担当はUI／API／DB／トラック状態を照合する。Macでの物理提示も本人の協力を得る。操作協力が得られない条件は未実施とする。
- 既承認の一時HTTPS中継では架空データ・専用資格情報／Cookieが経路を通る。カメラ映像とは区別し、映像は端末内処理のみ、音声要求・映像／音声の保存・外部送信は行わない。撮影対象は用意したテストバーコードだけ。実顧客・実決済・私物の商品／会員カードは使わない。
- テスト用の会員A／B・不存在会員、商品EAN-13／EAN-8／Code128、未登録商品、数量99用商品を主担当が準備する。EANは有効なチェックディジットと対応する架空DBコードを照合し、Code128には先頭ゼロ・大小文字を含む条件を用意する。表示コードとDBコードの対応を記録し、桁の補完・削除や大小文字変換をしない。

## 1. TC-03：会員Code128の最小確認

先にiPhoneで小さい一巡を確認し、成立したらMacの対応条件も個別に実施する。商品なし／あり、初回指定／AからBへの変更を区別する。各条件は前提とカート版を記録し、前条件から通常の明示操作で整える。

| 条件・本人の操作 | 確認する結果 |
|---|---|
| 会員専用ボタン→開始→会員Aを提示 | 入力先が会員と分かる。読取文字列を保持し、API確認成功後だけ会員確認成功を表示。会員確認後に読取領域・映像を閉じる |
| 商品ありで会員Bへ変更 | 商品行・追加時条件を保持し、成功後に保持候補で再計算。旧会員へ戻らない |
| 不存在会員を提示→新しい会員を再入力／非会員を選択 | PENDING中は旧額が参考表示。商品編集・購入は禁止、会員の再入力／再照会／非会員選択は可能。非会員化で旧ID・特典を解除する。追加の状態再確認をしない復帰も記録する |
| 主担当が正規会員要求の照会不能／応答不明を作る | 自動購入・別カート開始をせず停止。内容を保持し、元要求を明示照合してから許される選択へ進む。不存在の確定結果と区別する |
| 旧会員照会を保留→新会員／非会員を確定→旧処理を完了 | 新選択を旧結果で上書きしない。GET成功だけでPENDINGを解除しない。同画面・別タブ・直接APIの制限は主担当が対応条件として別記録する |

照会不能・遅着の制御は主担当が専用環境で到達点を記録して実施する。コード読取の成功だけを会員確定と扱わず、実サーバー処理の遅着とブラウザ応答到達を区別する。成立しない経路は模擬試験で代用合格にしない。

## 2. M5修正：確定拒否後の連続読取

両端末で、未登録商品と数量99の商品を別条件として実施する。

1. 商品カメラを開始し、未登録／数量99のコードを提示する。404 PRODUCT_NOT_FOUND／422 QUANTITY_LIMITと元の内容保持、追加成功表示がないことを確認する。
2. 主担当が再照合GETを保留し、その間に同コード・別コードを提示する。撮影を維持しつつ新規追加・購入・コードの蓄積を行わないことを確認する。
3. GET成功後も同コードを映し続け、エラーを反復しないことを確認する。別コードを提示し、ボタンの再押下なしで1個だけ追加する。
4. 対照としてGET失敗・401・別タブ通知競合を発生させる。撮影・新規受付を止め、未知結果の停止／再認証へ進み、画面へ戻るだけで自動撮影再開しないことを確認する。

この段階が不合格なら該当条件の連続読取を止め、操作順・HTTP・カート版・数量を記録して修正判断へ戻す。

## 3. TC-04：商品3形式と連続読取

| 本人の提示操作 | 確認する結果 |
|---|---|
| EAN-13、EAN-8、Code128をそれぞれ提示 | 正しい架空商品へ反映し、コードの先頭ゼロ・大小文字を保持。API反映後だけ成功表示 |
| 異なる商品を続けて提示 | 毎回のボタン押下なしで順に1個追加。商品名・現在数量・行強調が対応する |
| 同コードを映し続ける | 数量を増やさず、同商品案内だけ。通知・エラーを反復しない |
| 一瞬の欠落、ぼけ・遮蔽、枠外へ出して再提示を別実施 | 一瞬の欠落で再加算しない。意図した再提示で1個だけ増える。候補500msの誤解除の有無を実機条件とともに記録する |
| API待ちに同コード／別コード、会員PENDINGで商品読取を試す | 二重加算・待ちコードの蓄積なし。会員PENDINGの商品受付は禁止 |
| 商品追加の応答不明を発生させる | 読取停止、元の操作IDで照合。未保存と推測して別の追加を行わない |

読み取れない場合は距離・照明・提示媒体・方向を記録する。未検出を未登録商品と扱わない。500msの調整が必要なら、変更案・理由・影響と再試験範囲を示し、値を黙って変更しない。

## 4. TC-05：許可・終了・表示

| 本人の操作／主担当の観測 | 確認する結果 |
|---|---|
| 許可を拒否、起動失敗／カメラ利用不能 | 案内と手入力切替が使え、カートを保持。拒否後は本人が試験対象サイトだけの許可状態を変更して再試行し、全サイト設定を変更しない |
| バーコードを提示しない→閉じて手入力 | 認識案内を表示し、未登録エラーにしない。映像を止め、手入力できる |
| 許可待ち中に閉じる→取得が後から完了 | 後着トラックを直ちに停止し、映像・コールバックを再開しない。実ブラウザの許可UIが操作を遮る等で再現できなければ実施不能を記録する |
| 閉じる、商品／会員モード変更、背景移行、再認証、購入開始を別実施 | 元の読取回・トラックを停止。終了後コールバックで操作を送らず、戻っただけでは再起動しない |
| iPhone縦／横、キーボード表示、長い商品名、明細スクロール | 会員・担当者・数量・単価・値引き・税・合計・必要な操作が確認でき、欠落・重なりなし。長い名称を確認できる |

主担当は可能な範囲でトラックのreadyState、videoへのstream参照、終了後API要求の有無を読取確認する。画面が閉じたことだけでトラック停止を断定しない。実機操作が必要な条件を自動回帰だけで合格にしない。

## 証跡・停止・完了判定

条件ごとに端末版・build/hash、開始前状態、物理操作、コード／形式、要求・応答分類、反映版・数量・金額、映像停止の観測、判定を残す。記録は「確認」「不合格」「未実施」「実施不能」を区別する。画面証跡はカメラ映像や秘密値が入らない領域／DOMに限り、映像・音声・生Cookie・パスワード・秘密値入りHARを保存しない。

未知結果、対象カート／端末の不一致、二重加算、DB不整合、意図しない映像取得・送信、環境競合を確認した場合は対象の試験を停止し、主担当へ報告する。独立して安全な読取作業だけ継続する。失敗を操作のやり直しで隠さず、原因と修正後の再試験を分ける。

各段階の実証と欠陥探索レビュー後に条件別結果票へ記録し、両端末の未実施条件を残す。一方の成功や本票の準備完了をTC-03〜05全体／M5受入合格にしない。本人による主要フロー確認・受入は別に記録する。

終了時は主担当が今回のトンネル・アプリ・専用DBだけを停止し、公開URL閉鎖・3307／8443／8444の非待受を確認する。DB／volume／証跡を保持し、既存環境の削除・信頼設定変更・Azure・commit／push・本番反映は行わない。本票の戻し方は本票の差分だけを取り消すことであり、アプリ・DB・既存証跡を変更しない。
